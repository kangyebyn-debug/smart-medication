# 스마트 메디케이션 DB 설계서

- 작성일: 2026.11.17 / 2026.11.18 (문서 정돈: 상호참조 정리)
- 관련 문서: `01_기획서_v3.md`, `02_설계서_아키텍처_보안.md`
- 범위: 일반 구조화 데이터(Supabase)와 RAG용 벡터 데이터(Pinecone)를 분리 설계

---

## 1. 분리 설계 배경

- 범위 B(전체 의약품 데이터베이스를 RAG 대상으로 삼는 것)로 확정하면서, 전체 품목 텍스트를 청킹·임베딩했을 때 예상 용량을 추정한 결과 **0.8~1.5GB 수준**으로 나왔음 (품목 수 추정치 기반 추산이며, 정확한 수치는 6장 "검증 필요 항목" 참고).
- Supabase 무료 DB 용량(500MB)·Neon 무료(1GB)로는 이 규모를 감당하기 빠듯함.
- Pinecone 무료 Starter 플랜은 **저장 2GB, 쓰기 월 200만 건, 읽기 월 100만 건, 인덱스 5개**까지 무료 제공(2026.11.17 공식 가격 페이지 확인)되어 추정 규모를 여유 있게 수용 가능.
- 계정·저장약·채팅이력 등 일반 데이터는 용량이 작아 Supabase 무료 500MB로 충분하고, Auth·파일스토리지가 기본 포함되어 로그인 기능을 직접 구현할 필요가 없음.
- 결론: **일반 데이터는 Supabase(PostgreSQL), RAG 벡터 데이터는 Pinecone**으로 분리.

## 2. Supabase 스키마 (PostgreSQL)

### 2-1. `profiles`
| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| id | uuid | PK, FK → auth.users.id | Supabase Auth가 발급하는 사용자 id와 1:1 |
| display_name | text | nullable | 표시 이름 |
| created_at | timestamptz | default now() | |

> 비밀번호는 Supabase Auth가 자체 관리하므로 이 테이블에 저장하지 않음.

### 2-2. `saved_drugs`
| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| id | uuid | PK, default gen_random_uuid() | |
| user_id | uuid | FK → profiles.id, NOT NULL | |
| drug_name | text | NOT NULL | |
| product_code | text | nullable | 식약처 품목코드 (있는 경우) |
| created_at | timestamptz | default now() | |

인덱스: `(user_id)` — 사용자별 조회 최적화.

### 2-3. `chat_sessions`
| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| id | uuid | PK | |
| user_id | uuid | FK → profiles.id, NOT NULL | |
| title | text | nullable | 세션 제목(자동 생성 또는 첫 질문 요약) |
| created_at | timestamptz | default now() | |

### 2-4. `chat_messages`
| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| id | uuid | PK | |
| session_id | uuid | FK → chat_sessions.id, NOT NULL | |
| role | text | CHECK (role in ('user','assistant')) | |
| content | text | NOT NULL | |
| created_at | timestamptz | default now() | |

인덱스: `(session_id, created_at)` — 세션별 시간순 조회.

### 2-5. `prescription_extracts`
| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| id | uuid | PK | |
| user_id | uuid | FK → profiles.id, NOT NULL | |
| drug_name | text | NOT NULL | |
| dosage | text | nullable | 1회 용량 |
| frequency | text | nullable | 1일 복용 횟수 |
| timing | text | nullable | 식전/식후 등 |
| extracted_at | timestamptz | default now() | |

> **원본 이미지·OCR 원문 텍스트는 이 테이블에 없음** — 처방전 처리 파이프라인(`02_설계서_아키텍처_보안.md` 2-2절)에서 화이트리스트로 추출한 필드만 저장.

### 2-6. Row Level Security (RLS)

- 위 모든 테이블에 `user_id = auth.uid()` 조건의 RLS 정책 적용 — 각 사용자가 본인 데이터만 조회·수정 가능하도록 Supabase 기본 보안 기능 사용.

## 3. Pinecone 인덱스 설계

| 항목 | 값(안) |
|---|---|
| 인덱스 이름 | `drug-knowledge` |
| 차원 수 | 임베딩 모델 선택에 따름 (예: 1536) |
| 메트릭 | cosine |
| 메타데이터 필드 | `product_code`, `drug_name`, `chunk_type`(효능효과/용법용량/주의사항/병용금기 등) |

- 네임스페이스는 당장은 단일 네임스페이스로 시작 — 데이터가 늘어나면 `chunk_type`별 분리를 검토.

## 4. 데이터 적재 전략

- **초기 적재(배치)**: 공공 API에서 전체 품목 텍스트 수집 → 청킹 → 임베딩 → Pinecone에 일괄 upsert.
- **증분 갱신**: 식약처 허가 데이터가 연 단위로 갱신되는 특성을 고려해 주기적(예: 월 1회) 배치 재적재.
- **실시간 조회 영역은 그대로 유지**: 약품 검색·병용금기 확인(로그인 불필요 기능)은 지금처럼 공공 API를 직접 실시간 호출 — DB를 거치지 않음.
